# How to work with the protocol docs (`gitbook/`)

This repo publishes protocol documentation to a GitBook space from the `gitbook/` folder. Some of
that folder is source you write by hand; most of it is build output generated from Solidity NatSpec.
Editing the wrong part gets your changes silently overwritten (or rejected by CI). This doc says
which is which.

For the higher-level cross-package checklists (adding an Ark, a chain, an institution, etc.) see
[`AGENTS.md`](../AGENTS.md) / [`CLAUDE.md`](../CLAUDE.md) at the repo root — this doc is scoped to
the docs pipeline itself.

## The kinds of content

| Path                                                                                                                                                                                                                                                                                               | Who writes it   | How it gets there                                                                                                                               |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `gitbook/contracts/{core,dutch-auction,access,config,rewards,oracles}/reference/**`, `gitbook/contracts/libraries/{percentage,price,math}/`, `gitbook/governance/reference/**`, `gitbook/governance/voting-decay/`                                                                                 | Nobody, by hand | Generated by `forge doc` from Solidity NatSpec, post-processed by `scripts/docs/clean-forge-docs.mjs`, assembled by `scripts/docs/assemble.mjs` |
| `gitbook/SUMMARY.md`                                                                                                                                                                                                                                                                               | Nobody, by hand | Generated by `assemble.mjs` from `scripts/docs/summary.template.md`                                                                             |
| `gitbook/introduction/`, `concepts/`, `apis/`, `data/`, `security/`, `internal/`, the prose `governance/` pages (`overview.md`, `sip-process.md`, `staking-and-rewards.md`, `sumr-token.md`, `vesting.md`), `contracts/architecture.md`, `contracts/ark-catalog.md`, top-level `gitbook/README.md` | You, by hand    | Plain prose                                                                                                                                     |
| `scripts/docs/summary.template.md`                                                                                                                                                                                                                                                                 | You, by hand    | Controls nav order/labels for hand-written sections; the reference sections are a marker                                                        |
| `packages/*/README.md`, root `README.md`                                                                                                                                                                                                                                                           | You, by hand    | Not part of this pipeline at all — see "Package READMEs" below                                                                                  |

**Rule of thumb:** if a file lives under a `reference/` directory, under `contracts/libraries/` or
`governance/voting-decay/`, or is `gitbook/SUMMARY.md`, don't hand-edit it — your edit will be
silently discarded the next time someone runs `pnpm docs:build`, and if you commit a hand-edit that
drifts from a regeneration, `pnpm docs:check` (which runs in CI on every PR touching these paths)
fails the build.

## Regenerating

```bash
pnpm docs:gen      # turbo run docs:gen --cache-dir=.turbo — runs `forge doc` per configured package
pnpm docs:assemble # node scripts/docs/assemble.mjs — cleans forge-doc output + assembles gitbook/
pnpm docs:build    # docs:gen && docs:assemble
pnpm docs:check    # docs:build, then `git diff --exit-code -- gitbook/` — this is what CI runs
```

Run `docs:build` after touching anything that affects generated output — NatSpec comments, a
package's `foundry.toml` `[doc]` block, or `scripts/docs/summary.template.md` — and commit the
resulting `gitbook/` diff in the same PR/commit. `docs:check` will otherwise fail on `main`
(`.github/workflows/docs.yaml` runs the drift check on PRs and an auto-commit safety net on pushes
to `main`; Foundry is pinned to `v1.5.1` there because `forge doc` output format can shift between
versions and flap the check).

## 1. Contract reference (`gitbook/**/reference/`, `libraries/`, `voting-decay/`) — edit the NatSpec, not the markdown

The package → output mapping is `scripts/docs/docs.config.json` (currently 11 entries:
`core-contracts`, `gov-contracts`, `dutch-auction`, `access-contracts`, `config-contracts`,
`rewards-contracts`, `rwa-oracles`, `percentage`, `price-utils`, `math-utils`, `voting-decay`). To
change a reference page, edit the NatSpec comment on the contract/interface/error/event and
regenerate — nothing else works.

**Prerequisite per package:** `foundry.toml` needs `extra_output = ["devdoc", "userdoc"]` and a
`[doc]` block (`out = "docs/generated"`, `title`, `repository`), plus a `docs:gen` script in
`package.json` (`forge doc`). Without `extra_output`, forge omits the complete userdoc (event/error
notices, contract-level notice) from build artifacts — `forge doc` output looks fine but the
coverage auditor (below) reports false gaps.

### NatSpec gotchas that actually bite here

- **`@inheritdoc InterfaceName` on every override is required, not optional.** forge only copies
  docs across the inheritance edge when you write it explicitly — an override with no `@inheritdoc`
  and no docs of its own renders with an empty description on its generated page, even though the
  interface right above it is fully documented. See `packages/core-contracts/src/contracts/Ark.sol`
  for the pattern applied consistently across ~40 Ark overrides.
- **Split interface/error/event files** (`I<X>Errors.sol`, `I<X>Events.sol`) mean the `@notice` for
  an error or event must live on the **declaration in the interface file**. `natspec-coverage.py`
  (see below) dedupes events/errors package-wide by signature and only looks at the defining
  declaration — documenting a local re-declaration in the implementing contract doesn't count.
- **Multiple items declared in one `.sol` file are merged onto a single GitBook page**, ordered
  `abstract → contract → library → interface → function → struct → enum → error → event → constants`
  (`KIND_ORDER` in `clean-forge-docs.mjs`). The page's front-matter `description` is pulled from
  only the **first** item's summary — if that first-in-order item has a thin or missing `@notice`,
  the whole page gets no description even if later items on the same page are well documented.
- **Verify NatSpec against the actual implementation before writing it** — don't describe what a
  function is "supposed" to do from the name alone. This repo's NatSpec waves needed follow-up
  correction commits for exactly this: `getCurrentPrice` decimals (payment-token-native, not a fixed
  18), a DCA doc describing `previewDeposit` after the code had moved to `convertToShares`, vesting
  V2's `performanceGoals` being 1-indexed, and `InstitutionalVaultRegistry.removeInstitution`
  actually deleting data rather than soft-disabling it. Grep the function body, don't guess.

### What never gets a page

Anything under a `test?/`, `script?/`, `mock?/`, or `example?/` directory, anything with `Mock` in
the filename, or `*.t.sol` / `*.s.sol` files are matched by `EXCLUDE_RE` in `clean-forge-docs.mjs`
and silently skipped — no warning, no page.

### Git Source links are rewritten — don't fight it

`forge doc` embeds the current commit SHA into each page's "Git Source" link. Left alone, that link
(and thus the page body) would change on every single commit, permanently breaking the CI drift
check. `clean-forge-docs.mjs` rewrites every such link to
`https://github.com/OasisDEX/summer-earn-protocol/blob/main/<package>/<path>` — don't hand-edit
these back to a commit SHA.

### Adding a newly-documented package

Add an entry to `scripts/docs/docs.config.json` (`{package, section, out}`) **and** give that
package's `foundry.toml` the `[doc]` block + `extra_output` + a `docs:gen` script, then run
`pnpm docs:build`. Skipping the `docs.config.json` entry means `forge doc` output exists on disk
under `docs/generated/` but `assemble.mjs` never reads it — nothing shows up in `gitbook/` and
nothing errors.

### Proving a NatSpec-only change didn't touch executable code

`scripts/audit/check-comment-only.py <baseline-out-dir> <changed-out-dir>` diffs `deployedBytecode`
between two `forge build` `out/` directories, stripping the trailing CBOR metadata blob first (its
hash covers source text, so it legitimately changes on any comment edit even when the compiled
opcodes are identical — a factory's runtime bytecode can embed multiple such blobs from the
contracts it deploys, so the script strips every one it finds). Exit 0 means every matching artifact
has byte-identical executable bytecode. This is the bar every comment-only NatSpec wave in this repo
(Wave A across `access-contracts`/`config-contracts`/`dutch-auction`/`rewards-contracts`/
`rwa-oracles`/`chain-bridge`/`intent-system`/`voting-decay`, then Wave B on `core-contracts`/
`gov-contracts`) was held to before merging.

### Coverage auditing

`scripts/audit/natspec-coverage.py` cross-references each contract's ABI against solc's
devdoc/userdoc, resolving `@inheritdoc` so implementations that inherit interface docs count as
covered. Functions are audited per compiled contract, filtered to names actually declared in the
package's own source tree (so inherited OpenZeppelin/LayerZero members don't pollute the gap list);
events/errors are deduplicated package-wide by signature against their defining contract; items
invisible to the ABI (internal/private functions, modifiers, structs/enums) fall back to a
source-level doc-comment heuristic and are flagged `sourceHeuristic` rather than counted with
certainty. Reports land under `docs/audit/<period>/`.

## 2. Hand-written pages (`concepts/`, `apis/`, `data/`, `security/`, `internal/`, `introduction/`, `architecture.md`, `ark-catalog.md`) — free-form prose

Write these like any other markdown doc — prose, fenced code samples, diagrams — and link into
generated reference pages with relative links (e.g.
`../contracts/core/reference/contracts/arks/aave-v3-ark.md`).

**Verify claims against the real contracts/subgraphs before writing them.** A catalog row or concept
page describing "notable traits" from the protocol pitch rather than the actual `.sol` file is how
hand-written docs drift out from under the code they describe — same discipline as the NatSpec
gotcha above.

To add a new page under an already-published section, create the `.md` file and add one line to
`scripts/docs/summary.template.md` (that template is hand-edited directly; the
`<!-- @generated:contracts -->` marker inside it is what `assemble.mjs` expands into the generated
reference tree — don't add reference pages here by hand). Run `pnpm docs:build` afterward so
`gitbook/SUMMARY.md` picks up the new entry.

## 3. Package `README.md` files — a separate, unrelated system

`packages/*/README.md` and the root `README.md` are **not** part of the GitBook/NatSpec pipeline at
all — nothing generates them, nothing checks them against source, and `pnpm docs:gen`/`docs:check`
never touch them. They're hand-maintained package-level docs covering what a package does, its key
exports/contracts, build commands, and — the part that goes stale fastest — a cross-package
connections section describing how the package fits into the rest of the monorepo (see the READMEs
added across the contracts/shared-lib, deployment/ops, subgraph, and app/service packages for the
pattern).

Because nothing enforces them, they drift silently whenever the code they describe changes.
`AGENTS.md`/`CLAUDE.md` (repo root) have the same problem at a higher level — their cross-package
checklists reference specific file paths, config field names, and constants that get renamed or
removed. There is no automated check for either; keeping them accurate is a manual (or
agent-assisted) audit against the actual code, ideally done whenever a change touches the area a
README/checklist describes — see the "check the diff against a base commit, then update stale docs"
pattern for how to do this after merging upstream changes.

**Watch for `README.md` vs `README.MD` filename-case duplicates.** If you author or rename a README
on a case-insensitive filesystem (macOS, Windows) in a directory that already has one with different
casing, your editor/OS treats them as the same file, but git tracks them as two distinct paths — the
duplicate is invisible to you locally but real in the repo (both literally coexist on this repo's
Linux CI, and checkout on another contributor's case-insensitive machine produces an unpredictable
case conflict). Before adding or renaming a README, run `find <dir> -iname 'readme.md'` and confirm
there's exactly one hit.

## Where this fits together

- Changed a contract's behavior or added a parameter? Update the NatSpec on the interface/contract,
  run `pnpm docs:build`, commit the regenerated `gitbook/**/reference/` diff in the same change.
- Added a new Ark or protocol integration worth cataloging? Add a row to
  `gitbook/contracts/ark-catalog.md`, and follow the "Add a new Ark type" checklist in
  `AGENTS.md`/`CLAUDE.md` if it introduces a new `ArkType`.
- Restructured how a package depends on others? Update that package's `README.md` and check
  `AGENTS.md`/`CLAUDE.md` for any checklist that names the same files.
- Not sure which bucket a doc falls in? If `pnpm docs:build` would overwrite it, it's generated —
  don't hand-edit it, edit its NatSpec source instead.
